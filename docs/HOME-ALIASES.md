# Short home IDs and PIN invites

New homes receive a cryptographically selected, vetted alphabetic word alias strictly shorter than eight characters (maximum seven). Internal UUIDs remain immutable for SQLite relationships, membership/grants, SDK matchmaking, reconnect state, tickets and existing token invites. The additive version-two migration adds a case-insensitive unique alias column/index and leaves existing homes/data unchanged. Older homes continue using their original IDs. Version-one intentional capacity settings remain unchanged.

A bounded random collision retry falls back to a cryptographic selection from unused words. The finite pool fails atomically with HOME_IDS_EXHAUSTED/503 once exhausted: no suffix, eighth character, UUID fallback presented as a short alias, partial home or overwritten existing alias. This initial vetted dictionary is intentionally finite; future growth requires adding more vetted words under the same length limit.

Joining trims/lowercases the supplied alias or legacy UUID and resolves it internally before PIN checks, per-home rate limits, grants and ticket issuance. Different case/alias/UUID routes share the same brute-force budget. Home JSON and public listings add joinAlias, while homeId/id remain canonical. Display/copy chooses the alias when present. PINs remain required and hash-protected; aliases provide convenience rather than security.

Session info can copy a PIN-bearing invite link only from the current remembered, successfully admitted PIN. The PIN is in the URL fragment, never an HTTP query string, directory response, session token or account credential. Anyone holding this link can join using its PIN. The recipient immediately removes invitation credentials from the address bar, pre-fills Join with alias/ID and PIN, and must click Join. A pending invite suppresses automatic recovery of a previously active room and never auto-replaces another tab. Existing token invites retain their fragment flow. Stale/full/rotated-PIN/invalid-link failures are visible and require user correction; inactive durable homes can still be reopened under existing semantics.

The supplied screenshot showed Wildflower Hollow with an unknown PIN and a legacy UUID. A tab with no known PIN cannot derive it from the server's scrypt verifier; it must re-enter the PIN or ask the owner. If a known tab-local candidate merely has an older settings revision, Session info now re-verifies it with the server before displaying/copying it, then updates its revision. Rejected/rotated candidates are cleared. No plaintext server PIN store or permanent/cross-device PIN synchronization is introduced.
