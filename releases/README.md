# Maintaining the public Updates history

`history.json` is the versioned source for the footer. `schemaVersion: 1` is validated by `apps/web/lib/release-history.ts`, `pnpm releases:validate`, the unit suite and the root production build. Only `published` entries cross the server/client boundary in `app/page.tsx`; draft copy is not sent to browsers. No private GitHub access is needed to read the history.

Each entry has a stable unique `id`, `status`, `date`, `dateKind`, `title` and one or more plain-English `changes`. Published entries must be newest first. Use `YYYY-MM-DD` when only a day is established, or `YYYY-MM-DDTHH:mm:ssZ` for verified UTC seconds. Day-only releases appear before timed entries on the same day; that convention does not imply a particular release time. Dates must be real and not in the future. Drafts require `date: null` and `dateKind: "release"`. Unknown fields, duplicate IDs, malformed dates and empty copy fail validation. Evidence stays in repository documentation or private release handoffs, never the public JSON.

## Release checklist (release owner)

1. Every player-visible feature/fix release adds or updates a **draft** entry in this file. Summarize player impact, avoid spoilers, internal reports, identities, infrastructure/security details, test counts and private links. Gated features must not be described as active. Internal-only releases can omit an entry; document that decision in the release handoff.
2. Review the draft alongside the exact candidate head. Run `pnpm releases:validate`, `pnpm test`, `pnpm typecheck` and `pnpm build`. Check the footer on desktop/mobile, keyboard disclosure, oldest-history loading and game focus/fullscreen behavior.
3. Merge/deploy only through the designated release owner. A merge or successful build alone does not publish an entry. Keep it draft through the initial deployment and verify actual production behavior at the intended head.
4. After production verification, the release owner changes `status` to `published`, records the established release day or exact completion time, sets `dateKind: "release"`, and moves the entry into the published section in reverse chronological order. If only one service's rollout time is known, use the verified release day rather than implying an exact paired completion time. Re-run validation/types/build and deploy the metadata followup through the same release process. Do not use a guessed future timestamp to make the note appear during the initial rollout.
5. Confirm the live footer shows the new entry and hides remaining drafts. Record the exact head and date evidence in the release handoff. If production is rolled back, demote an entry describing absent behavior to draft until it ships again (or add a clearly dated public correction for a lasting change).
